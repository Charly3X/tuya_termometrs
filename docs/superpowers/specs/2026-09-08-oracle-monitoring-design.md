# Круглосуточный сбор статистики Tuya на сервере Oracle

Дата: 2026-09-08

## Проблема

Историю пишет сам виджет: каждый вызов `socket local` дописывает точку в
`power_history.json`. Когда домашний компьютер выключен, сбор останавливается.
За последние двое суток вместо ~24000 точек накопилось 8354 — остальное дыры.

Кроме того, температура и влажность не сохраняются вообще: в историю идут только
мощность и напряжение розеток.

Задача: собирать статистику непрерывно на сервере Oracle, а виджет должен брать
график оттуда.

## Проверенные факты

Всё ниже измерено 2026-09-08 на боевом аккаунте, а не предположено.

| Факт | Значение |
|---|---|
| Smart Life API работает из любой точки, подписка IoT Core не нужна | подтверждено |
| Латентность запроса к `apigw.tuyaeu.com` | медиана 61 мс, макс 208 мс |
| Ограничения по частоте | 192 запроса за 300 с — ноль ошибок |
| MQTT-пуш доставляет отчёты розеток | 27 событий за 90 с, оба устройства |
| Розетки декодируются из пуша | 11 dp-связей, включая `cur_power`, `cur_voltage`, `add_ele` |
| Датчик «Зал» декодируется из пуша | 4 dp-связи |
| Датчики «Спальня» и «Детская» из пуша **не** декодируются | 0 dp-связей, категория `tdq` |

Отдельно проверена причинность: розетка шлёт данные в облако **в ответ на
локальный опрос**, а не по своему расписанию. При опросе виджетом раз в 7 с
медианный интервал отчётов был 7.8 с; когда добавили локальные опросы раз в 2 с,
он упал до 3.0 с.

Отсюда следствие, которое надо принять осознанно: **с выключенным компьютером
частота отчётов неизвестна и, скорее всего, ниже.** Сервер до розетки локально
не дотянется, исправить это он не может. Мы сознательно не проектируем под
неизвестное число — коллектор покажет реальную картину за первые сутки.

## Архитектура

Три компонента, каждый чинится и перезапускается независимо.

```
Oracle                                             Домашний компьютер
┌────────────────────────────┐                    ┌─────────────────────┐
│ collector.py  (systemd)    │                    │ виджет KDE          │
│  MQTT-пуш ──────► SQLite   │                    │                     │
│  опрос shadow ──► SQLite   │                    │  живые значения:    │
└────────────────────────────┘                    │  локально, 7 с      │
┌────────────────────────────┐   HTTP + токен     │                     │
│ api.py        (systemd)    │ ◄──────────────────┤  график: с сервера  │
│  только чтение, порт 8080  │                    │  фолбэк на локальный│
└────────────────────────────┘                    └─────────────────────┘
```

### 1. `server/collector.py`

Единственный компонент, который пишет данные. Долгоживущий процесс под systemd
с `Restart=always`.

Два источника в одном процессе:

- **MQTT-пуш** для обеих розеток и датчика «Зал». Записывает каждый отчёт в
  момент прихода. Интервала как параметра нет.
- **Опрос shadow** раз в 5 минут для «Спальни» и «Детской» — у них сломано
  описание продукта в каталоге Tuya, пуш для них не разбирается. Эти датчики
  и так репортят раз в несколько минут, разрешение не теряется.

Обязательная деталь реализации: `Manager.refresh_mq()` использовать **нельзя**.
Он подписывается на топики устройств только при `set_up=True`, а у этого
аккаунта такого флага нет ни у одного устройства — подписка уходит только на
топик дома, куда отчёты приборов не идут. Проверено: 0 событий за 90 с.
Нужно строить `SharingMQ(customer_api, home_ids, devices)` напрямую со списком
устройств. С прямой подпиской — 27 событий за 90 с.

Ошибки: сбой облака пишется в лог, процесс продолжает работу. Переподключение
MQTT и ротацию токена SDK делает сам (`SharingMQ.run()` с нарастающей паузой).

### 2. `server/api.py`

Только чтение. Один эндпоинт:

```
GET /history?device=<id>&metric=power&hours=24
Authorization: Bearer <токен>
```

Отвечает `[[ts, value], ...]`. Порт 8080, простой HTTP без TLS — по решению
владельца данные о температуре и мощности не считаются секретными.

Токен нужен не ради секретности показаний, а чтобы посторонние не нагружали
эндпоинт. Отдельно важно: на сервере лежит `sharing_token.json` — это ключ
ко всему аккаунту Smart Life, включая управление розетками. Поэтому API не
имеет ни одного метода записи и не отдаёт содержимое сессии.

### 3. Изменения в виджете

`tuya_client.py history` сначала идёт в API с таймаутом 3 секунды. Если сервер
не ответил — молча читает локальный `power_history.json`, как сейчас. График
не ломается ни при выключенном сервере, ни при отсутствии интернета.

Живые значения не трогаем: розетки читаются локально раз в 7 секунд, как
сейчас. Виджет продолжает вести и локальную историю — она остаётся фолбэком.

## Хранение

SQLite вместо JSON. Текущий `save_history()` переписывает весь файл целиком при
каждой записи — 440 КБ каждые 7 секунд. При круглосуточном сборе это не жилец.

```sql
CREATE TABLE readings (
    ts     INTEGER NOT NULL,
    device TEXT    NOT NULL,
    metric TEXT    NOT NULL,   -- power | voltage | current | energy
                               -- temperature | humidity | battery
    value  REAL    NOT NULL
);
CREATE INDEX idx_readings ON readings(device, metric, ts);
```

Узкий формат: новые метрики добавляются без миграций, а частичные отчёты из
MQTT (приходит то `cur_power` один, то вместе с `cur_voltage`) ложатся
естественно — пишем только те метрики, что пришли.

**Единицы приводим при записи, а не при чтении.** Tuya отдаёт целые числа в
своих масштабах (`cur_power: 909` — это 90.9 Вт, `cur_voltage: 2365` — 236.5 В).
В базе лежат человеческие единицы: Вт, В, А, кВт·ч, °C, %. Иначе каждый
потребитель данных будет обязан помнить масштаб каждой метрики, и рано или
поздно кто-то ошибётся.

Объём при наблюдавшейся частоте — порядка 70 тыс. строк в сутки, около 2 ГБ в
год. Поэтому сырые данные храним **180 дней**, старше удаляем ночным
`DELETE`. Суточные агрегаты не делаем: дневной расход можно посчитать из сырых
данных, а `add_ele` розетка и так отдаёт накопительно.

## Перенос старой истории

Разовый скрипт `server/import_legacy.py` заливает существующий
`power_history.json` (8354 + 8257 точек, с 2026-09-06) в SQLite, чтобы график
не потерял прошлое.

## Авторизация на сервере

`tuya_auth.py` прогоняется **отдельно на сервере**, файл `sharing_token.json`
с компьютера не копируется. Причина: refresh-токен ротируется при обновлении,
и два клиента с одной сессией будут выбивать друг друга. Отдельный вход по
QR-коду даёт отдельный `terminal_id`, конфликта нет.

Обязательно: на сервере тоже нужен `prefer_ipv4()`. У `apigw.tuyaeu.com` есть
AAAA-записи, и без этого каждый запрос стоит ~180 с вместо 0.2 с.

## Конфигурация

На сервере — `server/config.json` рядом с сервисами: путь к базе, токен API,
порт, список устройств с их ролями (какие через пуш, какие через опрос).
Токен генерируется при установке, в репозиторий не попадает.

На компьютере — в существующий `config.json` добавляются два поля:

```json
"history_server": "http://<ip-сервера>:8080",
"history_token": "..."
```

Если `history_server` не задан, виджет работает ровно как сейчас, на локальной
истории. Это же и путь отката, если с сервером что-то не так.

## Развёртывание

- Два юнита systemd: `tuya-collector.service`, `tuya-api.service`.
- Порт 8080 открывается в Security List инстанса **и** внутри самой машины.
  У образов Oracle iptables по умолчанию режет всё кроме 22 — про это забывают
  чаще всего.
- Конкретную ОС определяем на месте: `cat /etc/os-release`.

## Тестирование

- `collector`: запись и чтение SQLite на поддельном источнике событий, без сети.
- `collector`: частичный отчёт MQTT (только `cur_power`) пишет одну метрику,
  а не затирает остальные.
- `api`: запрос без токена — 401; с токеном — данные; неизвестное устройство —
  пустой список.
- виджет: сервер недоступен — используется локальная история, график рисуется.

## Чего сознательно не делаем

- Не подбираем интервал опроса розеток — пуш снимает вопрос.
- Не строим веб-интерфейс: виджет и есть интерфейс.
- Не делаем суточных агрегатов и прореживания.
- Не поднимаем TLS и домен — решение владельца.
- Не переносим живое чтение розеток на сервер: локальные 7 секунд ценнее.

## Открытый вопрос

Реальная частота отчётов при выключенном компьютере. Узнаем из данных за первые
сутки работы коллектора. Если окажется слишком грубо, следующий шаг —
принудительное обновление командой из облака; в этой спеке этого нет.
