# Графики виджета: температура и розетки

Дата: 2026-09-08

## Проблема

График в виджете один и только для розеток: клик по карточке розетки открывает
полотно с мощностью. Единица «W» зашита прямо в подписи оси. По карточке
датчика клик не делает ничего — истории температуры в виджете нет вообще, хотя
сервер её уже пишет.

Код отрисовки лежит внутри `contents/ui/main.qml`, который разросся до 713
строк. Скопировать этот код ради второго типа графика значило бы дальше править
две копии парами.

Задача: графики для обоих типов устройств и приличная отрисовка.

## Что уже есть

- Сервер пишет `power`, `voltage`, `current`, `energy`, `temperature`,
  `humidity`, `battery`.
- В API два эндпоинта: `/history` (форма `[ts, power, voltage]`, её использует
  виджет) и `/series?device=&metric=&hours=` (произвольная метрика, не
  вызывается никем — отмечен в финальном ревью как мёртвый код).
- Периоды в интерфейсе: 1, 6 и 24 часа.
- Локальный запасной файл содержит только мощность и напряжение розеток.

## Что делаем

### 1. Компонент отрисовки

Новый `contents/ui/ChartCanvas.qml`. Принимает список серий, каждая со своими
значениями, цветом, единицей и привязкой к левой или правой оси. Оба графика —
одна реализация.

Это не украшательство архитектуры, а условие задачи: без выделения компонента
второй график означает вторую копию ста двадцати строк рисования.

### 2. График датчика

Две линии на одном полотне: температура (янтарная, шкала слева, °C) и
влажность (голубая, шкала справа, %).

Линия температуры **ровного цвета**. В виджете есть функция `getTempColor`,
красящая значение по зонам комфорта, но применять её к линии нельзя — линия
станет разноцветной и зарябит. Зональная раскраска остаётся на карточках.

### 3. График розетки

Одна линия мощности плюс строка сводки под полотном: минимум, среднее,
максимум и расход за показанный период.

**Расход считается интегрированием мощности**, а не по счётчику `add_ele`.
Счётчик сбрасывается в полночь, поэтому «за 24 часа» через него посчитать
нельзя. Сумма `мощность × интервал между отсчётами`, делённая на 3 600 000,
даёт кВт·ч и честна на любом периоде.

### 4. Единый путь данных

Новый режим:

```
tuya_client.py series <device_id> <hours> <metric[,metric]>
```

Возвращает:

```json
{
  "series": {"temperature": [[ts, v], ...], "humidity": [[ts, v], ...]},
  "device": "<id>",
  "source": "server" | "local" | "unavailable"
}
```

Розетка запрашивает `power`, датчик — `temperature,humidity`. Внутри это
несколько вызовов `/series`, но для виджета — один запуск процесса.

**Эндпоинт `/history` удаляется.** После этой правки его никто не вызывает, а
держать два эндпоинта, отдающих одно и то же в разной форме, — ровно та
дубликация, которую финальное ревью уже отмечало. Локальный фолбэк приводится
к той же форме `{"power": [[ts, v], ...]}`, чтобы форма была одна везде.

### 5. Прореживание

Сутки мощности при отчётах раз в 7 секунд — около 12 000 точек: примерно
400 КБ JSON и 12 000 отрезков на каждую перерисовку полотна.

Прореживаем в Python до **500 корзин**, беря из каждой минимум и максимум.
Простое «каждая двадцатая точка» срезало бы всплески — а всплеск потребления
это ровно то, ради чего на график и смотрят.

### 6. Подсказка при наведении

Вертикальная направляющая под курсором, значение и время. Для графика датчика —
оба значения сразу.

## Поведение при недоступном сервере

| Тип | Порядок |
|---|---|
| Розетка | сервер → локальный файл → «нет данных» |
| Датчик | сервер → «сервер недоступен» |

У датчика локального источника нет и не будет: час назад мы сознательно
решили, что сервер — единственный источник правды, а локальный файл лишь
аварийный кэш на шесть часов. Заводить второе хранилище температуры значило бы
отменить это решение.

## Чего сознательно не делаем

Ни зума, ни панорамирования, ни экспорта, ни периодов сверх 1/6/24 часов, ни
графика заряда батареи. Полотно шириной в пол-экрана этого не просит.

## Тесты

- Новый режим `series` возвращает объявленную форму для одной и для нескольких
  метрик.
- Прореживание сохраняет минимум и максимум каждой корзины и не теряет
  крайние точки.
- Прореживание не трогает ряд короче числа корзин.
- Расход: интегрирование мощности на известном ряде даёт известный ответ;
  ряд из одной точки не делит на ноль.
- Фолбэк: розетка при мёртвом сервере отдаёт `local`, датчик — `unavailable`,
  пустой ответ сервера считается отсутствием данных, а не данными.

QML юнит-тестами здесь не покрыть — проверяется установкой и осмотром.

## Установка

Единственная часть этой работы, которая трогает QML, поэтому в конце нужно
скопировать `main.qml` и `ChartCanvas.qml` в каталог плазмоида и перезапустить
`plasmashell`. Правки Python подхватываются сами.
